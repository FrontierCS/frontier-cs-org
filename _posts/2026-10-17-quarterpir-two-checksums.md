In its [FrontierCS 2]({{ '/#leaderboard' | relative_url }}) run on the QuarterPIR task, Muse Wonder 1.0 cut the bytes of each private lookup by 27%, with privacy unchanged. The fix is a trick from RAID-6 disk arrays: two checksums can rebuild two lost values. Twelve models ran the task, and seven passed. No other passing run saved more than 96 of the 1,760 bytes per lookup. Muse Wonder 1.0 saved 480.

## The Task

FrontierCS 2 turns published papers into tasks. Each task removes the key part of the code the authors released, which serves as the human reference. Every model on the [leaderboard]({{ '/#leaderboard' | relative_url }}) gets one run per task, in its own coding agent, with a 5-hour budget. Its final version is scored on hidden workloads. It passes only if it beats the human reference on every metric of every workload.

QuarterPIR, a EUROCRYPT 2024 scheme by Ghoshal, Zhou and Shi [1], lets a client read one database entry without the server learning which. The [task]({{ '/task/#quarterpir' | relative_url }}) removes the server's request handler. The agent may redesign the client and both messages. The server may see only a fixed public function of the request the authors' client would send. A pass needs fewer bytes on every lookup, faster server, setup and lookup times, no more client memory, and the right entry every time.

## The Scheme on 16 Entries

Take a database of 16 entries in four rows:

<pre class="grid16"><code>row 1:   A  B  C  D
row 2:   E  F  G  H
row 3:   I  J  K  L
row 4:   M  N  O  P</code></pre>

Ahead of time, the client picks a hint, one position per row, say B, G, I and O. It stores only their XOR, the parity $$h$$. To read G, it swaps G for a spare entry F whose value it knows, and asks the server for the parity of B, F, I and O. Values that appear twice cancel:

$$h \oplus (B \oplus F \oplus I \oplus O) = G \oplus F.$$

One more XOR with F gives G. The server sees one position per row and cannot tell which one was swapped.

A real database has thousands of rows, so the request sends keys instead. A short key expands to one position in each row of a group. Here rows 1 and 2 form group 1, and rows 3 and 4 form group 2. The group of the wanted entry goes as an explicit list, and its key is replaced by random bytes. The server cannot tell which group the list belongs to, so it answers for every group. It computes each key parity $$K_b$$, the XOR of what key $$b$$ picks in its group. It then forms one candidate per group: the list applied there, plus the key parities of the other groups. The client keeps the candidate of its own group.

## Why Every Reply Carries the Key Parities

A hint serves one lookup, since reusing it would repeat its keys. After reading G, the client takes a backup hint for row 2, say A, H, L and M. It swaps H for G and updates the parity. Ghoshal, Zhou and Shi [1] show that this refresh keeps the table of hints distributed as before, so the server learns nothing from later requests.

The swap leaves a gap: the keys of the new hint still pick H, not G. Say the client later reads M with this hint. Group 1 must then go as a key that picks G. QuarterPIR draws random keys until one does, and that key picks another entry of row 1, say D. The client is left with the error A ⊕ D. It cannot remove it alone, because it does not know D. The server key parity $$K_1 = D \oplus G$$ removes it.

The client cannot ask for $$K_1$$ alone, since that would reveal where its last read lay. So every reply carries every key parity. At full size there are 32 groups, and the key parities take 512 of the reply's 1,024 bytes. The client uses at most one of them, and only after a refresh.

## The Two Checksums

Muse Wonder 1.0 sends two sums of the key parities instead of all 32. The server's list $$K_b$$ and the client's own parities $$P_b$$ agree in every group but two. They differ by $$v$$ in group $$i$$, which holds the wanted entry, and by $$u$$ in group $$j$$, which holds the inserted one. The client knows $$i$$ and $$j$$ and needs only $$u$$.

Ordinary numbers show why two sums suffice. Say the server's list is 4, 7, 1, 9 and the client's is 4, 2, 1, 6, differing in groups 2 and 4. The server sends its sum, 21, and its sum weighted by 1 to 4, which is 57. The client's own sums are 13 and 35. The differences give $$u + v = 8$$ and $$2u + 4v = 22$$, so $$u = 5$$.

QuarterPIR's version uses XOR for addition, and products in the field with $$2^{128}$$ elements for the weights, so each sum stays 16 bytes:

$$T = \bigoplus_b K_b, \qquad T_w = \bigoplus_b w_b K_b.$$

The client's plain sum is its hint parity $$h$$. Its weighted sum $$h_w$$ costs one extra stored value per backup hint. Groups where the lists agree cancel, which leaves two equations in two unknowns:

$$h \oplus T = u \oplus v, \qquad h_w \oplus T_w = w_j u \oplus w_i v.$$

The reply drops from 64 values to 34, or from 1,024 bytes to 544. A lookup drops from 1,760 bytes to 1,280.

## Why Privacy Is Unchanged

The benchmark fixes what the server may see. For every lookup, the trusted harness computes the authors' request itself. It hands that request, and nothing else, to the solution's reduction function in a separate process. The client must send exactly the reduced bytes, and the server gets the harness's copy. The server's view is thus a fixed public function of the original view, so it cannot learn more. The reply needs no rule, since the server computes it. Muse Wonder 1.0 sends the authors' request unchanged on the large database; only the reply changed.
