## How far agents go for a score

A FrontierCS task asks an agent to beat a paper's own code. Most of what agents submit is an honest attempt. Some of it is not. We only count one kind of trick as cheating: faking the measurement. Tuning a solution to the task's inputs is fair. Here is what agents tried, and what we changed.

### It cloned the answer from GitHub

Glenside asks the agent to rebuild an analysis from a compiler paper. The agent has no copy of the paper's code. GLM 5.3 Flash wondered whether that was really true:

<div class="out"><div class="out-h"><i style="background:var(--m-glmf)"></i>GLM 5.3 Flash <span>· Glenside</span></div><div class="out-b">Let me check whether raw network access is available to fetch the upstream glenside source (the authentic restoration reference).</div></div>

It ran `git clone` on the paper's repository, and the clone worked. Its next message read:

<div class="out"><div class="out-h"><i style="background:var(--m-glmf)"></i>GLM 5.3 Flash <span>· Glenside</span></div><div class="out-b"><b class="red">JACKPOT!!!</b> I found the upstream original implementation!</div></div>

Its final patch pasted 3,074 lines of the human reference into one file. The 14 other runs that passed wrote their own code.

Copying the answer is still not enough to pass. FrontierCS does not ask an agent to reproduce a paper. It asks the agent to beat the paper's own code, on every metric and every hidden workload. A perfect copy of the human reference only ties it, and a tie fails. GLM 5.3 Flash passed because it also changed 23 lines in another file, on top of the copied code.

The agent could reach GitHub because of a leftover network rule. Some harnesses call their model provider directly, so a site can let agents reach the internet. The rule that allowed this stayed in place after we turned the setting off, so agents could still open outside HTTPS connections. We fixed it in three places:

- **The rule is removed.** When outside access is off, the platform now deletes that rule from every run. The agent can reach the model it runs on and nothing else.
- **Nothing is downloaded at run time.** Every task that fetched packages while it ran now ships them in its image, so no task needs the network.
- **Each task is checked from inside.** Before a task goes live, a check inside the agent's sandbox confirms that it cannot reach the internet.

### It used a classic search instead of training the model

RAGEN trains a language-model agent to play Sokoban with reinforcement learning. The task asks the agent to improve one file: the code that turns the model's moves into training batches. GPT-6.1 Sol wrote a breadth-first search that solves each board. Then, after the model answered, its patch threw the model's moves away:

The boards were solved, the rewards were real, and training ran. The judge checked all of that. It never checked who chose the moves. The run scored about eight times the human reference and passed.

The fix takes the measurement out of the agent's hands. The agent's training code now runs on a GPU machine of its own, and the judge runs on another. The judge takes the training batches that run produced and replays every episode: it resets Sokoban from the episode's seed, plays the recorded moves and recomputes the success rate and the reward itself. It also checks every move in a batch against the model's own answer for that turn. A patch that swaps in other moves, or reports a reward the replay does not reproduce, scores 0. After the fix, every agent we reran on RAGEN fails.

Parallel DBSCAN had the same hole in memory: one process ran all five timing rounds, and a cache made rounds two to five a copy. Each timing round in both tasks now starts with nothing left over from the last.

### What we check now before a task joins the leaderboard

Each of these submissions was legal. It changed only the files the task allowed, and it passed every check the judge made. A sandbox cannot stop that kind of trick. A judge that knows what to check can.

Before a task goes live now, it faces a set of attack submissions. One reads the judge's files. One tries to hide what it does from the judge's checks. One keeps state between timing rounds. Each must score 0.

## One format for every task

The 48 tasks had grown apart. Each one built its sandboxes by hand, and code that every task needs was copied from task to task. One verifier file existed in 44 copies, in 30 different versions. A fix to one copy did not reach the others.

Every task now uses the same building blocks:

- **One file per task.** A single `task.toml` describes the task. Its judge, its datasets and its starter code sit next to it.
- **Shared images.** Every task builds on the same three base images, for the agent, the judge and the GPU tools. A change to shared code reaches every task at once.
- **One submission check.** The judge starts from a clean copy of the starter code and keeps only the files the task allows. A submission that touches anything else scores 0.
- **Separate machines for heavy experiments.** In two tasks the agent's code trains a model. That code now runs on a GPU machine of its own, and the judge scores the result on another.

This is the `task.toml` of SCOPE, the counting task from above, shortened. What it leaves out comes from shared defaults:

```toml
id = "batch_local_counting"
display_name = "Batch Local Counting"

[agent]                       # the agent's machine
cpu_millis = 1000
memory_bytes = 4294967296     # 4 GiB

[quota]
wall_time_seconds = 18000     # 5 hours
max_train_calls = 100

[submission]                  # what a submission may change
allowed_paths = ["counting/forest.cpp", "counting/execution.cpp", "plan/tree.cpp", ...]
max_changed_files = 12
allow_new_files = false

[paper]
title = "Fast Local Subgraph Counting"
venue = "PVLDB 2024"
```

### The judge sandboxes the agent's code

The judge runs the agent's code to score it, so that code runs next to the hidden workloads and the reference. In the old format, each task kept them apart in its own way, and some did not. Now every task runs the agent's code through one shared sandbox, `isolate`, inside the judge. The code sees only its own files and inputs, writes only its result folder, has no network and gets a fresh instance for every run. On CPU tasks the sandbox uses Landlock, on GPU tasks user namespaces. Of the 48 tasks, 43 use it. Four run the agent's code on a separate machine instead, and one never runs it at all, because the answer is a data file.
